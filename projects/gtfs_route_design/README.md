# 5·6장 통합 과제 — 신규 셔틀의 GTFS와 경로 효과

5장에서 GTFS 구성과 작은 시간표를 읽고, 6장에서 환승 경로와 라운드 갱신을 학습한 뒤 진행합니다. 기본 구현과 별도로 GTFS 작성과 신규 노선의 효과를 분석하는 과제입니다.

실행 파일은 [route_design.ipynb](route_design.ipynb)입니다. 저장소 루트에서 다음 명령으로 열 수 있습니다.

```bash
jupyter lab projects/gtfs_route_design/route_design.ipynb
```

노트북은 데이터를 처음부터 읽습니다. 5·6장 노트북을 같은 커널에서 미리 실행할 필요가 없습니다. 학생 RAPTOR의 완성 여부와 관계없이 제공된 탐색 함수로 경로를 비교합니다.

## 시작하기 전에 설명할 것

- `routes` 한 행, `trips` 한 행, `stop_times` 한 행은 각각 무엇인가요?
- 정류장 네 곳을 지나는 운행 여섯 편에는 방문 기록이 몇 행 필요한가요?
- 준비 시각 08:00과 08:10에 대해 08:05 차의 탑승 가능 여부는 어떻게 다른가요?
- 탑승 횟수와 환승 횟수를 어떻게 구분하나요?

기본안은 하남시청→하남문화예술회관→미사강변브라운스톤→미사역의 가상 단방향 셔틀입니다. 구간시간은 4분·8분·2분이며 정차시간은 0초입니다. 정류장 위치는 기존 자료를 사용하고 시간은 설계 가정으로 둡니다.

## 1단계 — GTFS 작성과 재입력

07:05부터 09:00 미만까지 20분마다 출발하므로 운행은 여섯 편입니다. 첫 편의 시각을 먼저 종이에 적고, 누적 구간시간과 코드 결과를 대조합니다. 이 기본안은 2026-09-23 하루만 운행합니다.

| 파일 | 기본안 행 수 | 먼저 설명할 관계 |
|---|---:|---|
| `agency.txt` | 1 | 가상 운영기관과 시간대 |
| `stops.txt` | 4 | 정류장의 이름·좌표·식별자 |
| `routes.txt` | 1 | 노선과 운영기관 |
| `trips.txt` | 6 | 각 출발편과 노선·운행일 |
| `stop_times.txt` | 24 | 운행별 네 정류장의 방문 순서·시각 |
| `calendar.txt` | 1 | 운행하는 하루의 적용 기간 |

노트북은 식별자·시간 순서를 검사하고 여섯 TXT를 ZIP에 저장한 뒤 다시 읽습니다. `validate_feed`만으로 전체 GTFS 명세를 검증했다고 보지는 않습니다. 운영기관은 가상이며 URL은 예시 주소입니다.

노선도와 설계 조건표에서 정류장 순서와 구간시간을 대조합니다. 지도 선은 정류장의 방문 순서이며 도로를 따라 계산한 주행 경로가 아닙니다.

## 2단계 — 두 출발시각의 경로 비교

비교 조건은 하남시청 정류장 출발, 미사강변브라운스톤 정류장 도착, 최대 다섯 번 탑승입니다. 운행 날짜와 출발·도착 정류장, 접근 조건은 기존·신규 추가 두 안에서 같습니다. 6장 기본 실습의 건물 좌표에서 접근하는 조건과 구분합니다.

기본안의 셔틀은 08:05에 출발해 08:17에 목적 정류장에 도착합니다. 08:00과 08:10의 승객이 이 차를 탈 수 있는지 예상하고, 두 시각만 먼저 실행합니다.

| 정류장에 준비된 시각 | 기존 통행시간 | 추가 후 통행시간 | 환승 횟수 |
|---|---:|---:|---|
| 08:00 | 22.9분 | 17.0분 | 1회 → 0회 |
| 08:10 | 18.6분 | 18.6분 | 2회 → 2회 |

표의 숫자는 제공된 하남 자료와 교육용 RAPTOR의 결과입니다. 실제 운행의 관측 결과는 아닙니다. 첫 요청은 셔틀을 타고 두 번째 요청은 기존 경로를 선택하는 이유를 설명한 뒤 다음 단계로 넘어갑니다.

## 3단계 — 출발시각과 배차간격 확대

07:00~08:55를 5분 간격으로 나누어 24개의 요청을 비교합니다. 기본 노선과 추가한 노선이 함께 있으므로 시각별 이용 노선을 읽어 어떤 경로가 선택됐는지 확인합니다. 미도달은 빈값으로 남깁니다.

20분 기본안을 확인한 뒤 정류장 순서·구간시간·배차간격 중 하나 이상을 바꾸어 자기 안을 만듭니다. 10분 간격안은 `scenario_name = "my_shuttle_10min"`으로 별도 저장합니다. 같은 시간 범위의 운행은 열두 편으로 늘어납니다.

각 안을 비교할 때는 원래 하남 시간표에 한 번씩 추가합니다. 두 안을 누적해서 붙이지 않습니다. 같은 이름으로 실행하면 해당 폴더의 산출물을 갱신하므로 안마다 다른 폴더 이름을 사용합니다.

## 자료를 합치는 범위

이 과제는 기존 정류장의 식별자·이름·좌표를 유지합니다. 정류장 자체를 새로 만드는 작업은 별도 확장입니다. 신규 ZIP은 표준 버스 코드 `3`을 쓰고, 하남 복사본에 합칠 때만 실습 코드 `0`으로 바꿉니다. 원래 ZIP과 하남 원본은 유지합니다.

비교 날짜의 요일·기간으로 두 자료의 운행을 먼저 선택합니다. 이 날짜 선택은 `calendar`를 사용하며, 다른 피드의 `calendar_dates`나 전날에서 이어지는 심야 운행은 처리하지 않습니다.

[신규 노선 설계 화면](../../_static/ch05_gtfs.html#builder)은 TXT 원문을 살펴보는 선택 도구입니다. 화면의 기본안은 이 노트북과 출발 범위·정류장 수·정차시간이 다르므로 행 수를 그대로 비교하지 않습니다. 과제의 전후 비교는 노트북에서 만든 기존 정류장 기반 ZIP으로 진행합니다.

## 제출물

산출물은 `outputs/<scenario_name>/`에 저장합니다.

| 파일·설명 | 확인할 것 |
|---|---|
| `gtfs.zip` | 여섯 TXT, 식별자 연결과 방문 시각 |
| `route.png`, `design.csv` | 정류장 순서와 운행 조건 |
| `comparison.csv`, `comparison.png` | 같은 요청에 대한 기존·신규 추가 결과 |
| 설계 이유 3문장 | 어떤 조건을 왜 바꾸었는가 |
| 경로 비교 설명 | 개선된 시각과 개선되지 않은 시각 각 하나 |
| 대안 비교 | 단축시간과 추가 운행 편수를 함께 기록 |

출발시각별 결과를 승객 수요로 가중한 평균처럼 해석하지 않습니다. 차량 회차·기사 근무·운영비는 계산하지 않으므로 시간 단축 결과만으로 실제 운영안을 확정하지 않습니다.
